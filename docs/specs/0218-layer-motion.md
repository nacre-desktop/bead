# B0218: compositor-driven layer-surface motion

## Goal

Let a layer-surface client submit one rendered buffer atlas and ask a compositor to animate its presentation planes at the output refresh rate. The optional protocol must remain useful to any Wayland shell framework; it contains no application identity or product paths. Clients that do not find the global keep the existing frame-driven renderer unchanged.

## Protocol contract

The MIT protocol is `protocols/bead-layer-motion-v1.xml`, interface `bead_layer_motion_manager_v1` version 1. A client binds the manager and calls `get_motion(new_id, wl_surface)` for a surface already assigned a layer-shell role. The returned `bead_layer_motion_v1` object manages multiple planes that sample rectangles from the same surface buffer, in creation order; the first plane is behind later planes. `add_plane(id, source_rect, from_rect, clip_rect, opacity)` defines an immutable source rectangle and its initial presentation. `set_plane_from` and `set_plane_to` update the starting and target states for later animations; `set_curve` selects the shared curve; one `animate(serial, duration_ms, retarget)` starts all configured planes together. `set_plane_opacity_mode` selects linear opacity or opaque-above-threshold behavior for a plane. In threshold mode the compositor first interpolates opacity, then returns 1 when that value is greater than `threshold_millionths / 1,000,000`, otherwise it returns the interpolated value. A threshold of 1,000 exactly matches Bead's current panel opacity rule. `cancel(serial)` freezes the current presentation. The request batch takes effect atomically with the next `wl_surface.commit` for that surface. Thus the client can attach its complete atlas and all planes in one commit, with no intermediate open-pose flash. The compositor starts the shared clock on the next predicted output presentation after that commit.

Source rectangles use logical coordinates in the surface texture after buffer transform and viewport mapping. Destination and clip rectangles use signed/unsigned Wayland fixed-point logical surface-local units, independent of output scale. Destination rectangles may translate and resize each sampled plane. Clip rectangles are fixed in the unanimated layer-surface frame, applied after destination placement; this lets content move behind a stationary reveal boundary. A zero width or height means an empty clip. `opacity` is normalized fixed-point in [0,1]. The compositor intersects each clip with the surface and output bounds. Scale conversion and fractional output placement belong to the compositor, so a 1.5 output scale must not cause client-side resampling or changed logical geometry.

Curve enum values are `linear`, `ease_out_cubic`, `ease_in_out_cubic`, `emphasized_accelerate`, and `spring`. Their normalized progress equations are respectively `t`, `1-(1-t)^3`, `4t^3` for `t<0.5` else `1-(-2t+2)^3/2`, `t^4`, and `(1-(1+8t)e^(-8t))/(1-9e^(-8))`, where `t` is clamped to [0,1]. Values interpolate component-wise from the start tuple to the end tuple. The formula definitions make the protocol independent of CSS interpretations and preserve Bead's motion-token behavior.

A normal animation interpolates every plane component-wise from its `from` tuple to its `to` tuple on one shared timeline. A retarget samples the currently presented tuple for every plane at the new start time and ignores all newly supplied `from` tuples, then interpolates to the new targets over the requested duration. Serial values identify the latest group request. On completion or cancellation, one `plane_state(id, final_tuple)` event per plane precedes `done(serial)` or `cancelled(serial)`. Cancellation covers explicit cancel, replacement, surface unmap, and destruction. Completion/cancellation commits the final sampled tuples as static presentation state. Stale serials do not affect the current animation. Destroying either object cancels any active animation.

The compositor owns presentation only: clients still own buffers and update content when that content changes. While an animation is active, the compositor samples each plane from the same texture and recomputes destination, clip and opacity at each output presentation without requiring client commits. Input is constrained by the union of effective animated clips and destination bounds; clients may still provide their final input region with ordinary surface state. Damage, screenshots, screencasts and output migration must observe the same sampled presentation as scanout. `reset` is staged with the next root surface commit: it cancels any active timeline at its sampled state and clears plane definitions/presentation transforms atomically with replacement ordinary content. Clients use it when abandoning an atlas, and must not send it before a replacement buffer is ready to commit. Plane motion applies to client buffer content; layer-role geometry, exclusive zones, compositor decorations, and rule-defined effects remain under their existing owners unless the client includes them in its atlas.

## Rendering semantics and limits

A single plane cannot change the shape of pixels already baked into its source rectangle. Multiple atlas planes can preserve independently moving content and body artwork when the client can rasterize those pieces once and express each as a translated/clipped/resized rectangular patch. Existing edge-template decomposition provides a candidate: a clipped open-state art crop, a moving edge band, and a content plane. Very small reveals, where the edge joins rounded artwork and its shadow interact, need an exact precomputed atlas or must stay on the existing frame-driven path. The client must not silently approximate a pose the plane set cannot represent.

## Bead client behavior

`bead-wayland` feature-detects the manager from the registry. The initial exact Bead client planner supports whole-scene closing motions and plain openings whose `reveal` flag is false. It rejects growing-body openings, periodic scene motion, reduced-motion state, compositor background-blur effects, invalid geometry, atlases larger than 64 MiB, and any direction where rendered ink outside the viewport could move into view. Eligibility uses conservative vector paint bounds and exact scale-specific bitmap/raster pixel footprints, not only the logical scene viewport. Bitmap edges follow the renderer’s rounded physical origin and raster dimensions. Eligibility compares against the allocated physical atlas extent at fractional scales, while protocol source, destination, and clip rectangles remain in the unchanged logical surface coordinates; clips remain ignored and unknown extents fall back safely. Those cases retain the current CPU frame path; the client must not flatten a growing rounded body, omit hidden pixels that enter from a clipped edge, or approximate an independently animated compositor effect. For a supported slide, the renderer rasterizes its atlas once and submits the plane set and shared animation in the same commit as the complete buffer. It requests one initial frame callback and presentation feedback for readiness and UI bookkeeping, then requests no frame callbacks while the compositor owns the timeline. Reversals retarget the same attached atlas from the compositor's current sampled pose, with one group animation request and no repaint. A handoff from the frame-driven path is allowed only when its sampled openness is already at the target transition's exact starting endpoint (closed for opening, open for closing); a mid-flight CPU reversal remains on the frame-driven path. Once the compositor owns the timeline, plain reversals continue to retarget its sampled pose. Reopening a growing-body reveal resumes frame-driven rendering. The client attaches the current CPU reveal pose and stages `reset` in that same surface commit, preserving the old atlas and sampled presentation if painting or buffer acquisition must retry. The first visible buffer must already contain the exact pose at the animation start, and close motion must preserve its established exit geometry. Content changes during an active motion may submit one updated atlas without restarting the compositor animation.

Atlas storage is bounded by `4 × physical_width × physical_height` bytes, capped at 64 MiB per active plan. The client uploads those pixels into its existing reusable shared-memory pool; freed compositor slots are reused after release. The renderer drops its temporary pixel vector after upload but retains the budget charge until completion or cancellation.

## Verification

Protocol tests cover tuple interpolation, clipping, opacity, each curve, retargeting, cancellation and unmap. Bead tests count one paint and one group animation request per supported slide, preserve legacy behavior with no global, and compare pixels at sampled times where a complete target presentation can be composed from animated planes. Include fractional scale 1.5 coverage. A measured client-CPU comparison must separate one-time paint cost from active-slide per-frame cost; compositor-side frame work and live acceptance are measured by the compositor integration and system owner.

## Runtime CPU sample

An ignored private compositor harness exercised the public Bead runtime in an optimized release build (`opt-level=3`, `codegen-units=16`, LTO off) against a 120 Hz synthetic output. The fixture used a 1572×1071 logical surface at scale 1.0, 240 rounded primitives, and a 600 ms opening. CPU was sampled from 50 ms through 580 ms after the first buffer commit using `/proc/<pid>/task/<pid>/schedstat` for the UI thread and `clock_getcpuclockid` for the whole client process. Over the full slide, the CPU path painted and attached 74 buffers, committed 75 times, and requested/completed 74 frame callbacks; in the 64-refresh CPU sample window, 64 callbacks were delivered. UI-thread and process CPU in that window were both 277.501 ms total (4.336 ms per refresh). The compositor path painted and attached once, committed twice, submitted one animation request and one initial frame callback, and delivered no callbacks during the sample window; UI-thread and process CPU were both 0.120 ms total (0.00188 ms per refresh). The measured ratio is about 2,300× for this fixture only. This synthetic scale-1 result does not predict laptop performance at scale 1.5 or cover growing-body reveals.

## References

This spec preserves the opening-pose readiness rule, committed-frame scheduling, exit poses, content-layer behavior and battery measurements captured by the framework's preceding panel-motion and rendering specifications. These references define existing behavior; this proposal changes how representable presentation motion is scheduled.
